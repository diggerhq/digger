---
title: "Plan artifacts"
---

Digger can be used to store plan artifacts during the plan phase and make them available for use during the apply phase. Once plan artifacts are configured and uploaded during the plan phase
they will automatically be used during the apply phase. Once one of the below artifacts is configured successfully there is no additional configuration needed on your end to achieve apply-time artifact reuse.

### Github 
Digger can use Github Artifacts to store `terraform plan` outputs. In order to enable it you can set the following argument in digger_workflow.yml:

```
upload-plan-destination: github
```

<Warning>
    Github plan artifacts as a destination is currently deprecated due to a change in Github API. For more information see [this issue](https://github.com/diggerhq/digger/issues/1702).
</Warning>

### GCP 
You can also configure plan outputs to be uploaded to GCP Buckets instead. This is handy in case you want your plan outputs to stay within your organisation's approved storage providers for security or compliance reasons.

To change digger to upload the plan to GCP set the follow argument in the digger_workflow.yml file

```
with:
    google-lock-bucket: 'gcp'
    upload-plan-destination-gcp-bucket: 'terraform-plan-output-1239123'
```

### AWS 
You can also use AWS S3 buckets to store plan outputs.  

To change digger to upload the plan to AWS S3 set the following arguments in the digger_workflow.yaml

```
with:
    upload-plan-destination: 'aws'
    upload-plan-destination-s3-bucket: 'terraform-plan-output-1239123'
```

With S3, Digger uploads a `.txt` copy of the human-readable plan output. The PR
comment links to it, so you can still read the whole plan when the comment has
to be trimmed to fit GitHub's character comment limit.

The full-plan link is a pre-signed S3 `GetObject` URL, so opening it does not
require an AWS console session. It is created as the comment is published and
is valid for up to one hour. Links in older comments are intentionally not
refreshed and will eventually expire.

The bucket and object remain private. A pre-signed URL is a bearer credential:
anyone who has the URL can temporarily read that one `.txt` object. Use this
feature only where pull request comments are visible to trusted users. The AWS
principal used by Digger must have `s3:GetObject` permission for the `.txt` key.
If the object uses SSE-KMS, the principal also needs the existing `kms:Decrypt`
permission.

Bucket policy conditions still apply to pre-signed requests. For example, a
policy requiring a particular VPC endpoint or source IP can prevent a
reviewer's browser from opening the link. CORS configuration is not required
for ordinary browser navigation to the URL.

When Digger uses temporary AWS credentials, the link expires at the earlier of
the requested one-hour lifetime and the credential session's expiration. The
action's default role session lasts one hour and begins before planning, so the
link may remain usable for less than a full hour. To provide a full hour after
comment publication, set `aws-role-duration-seconds` high enough to cover both
the run duration and the desired link lifetime.

You can also use Azure storage accounts to store plan outputs.

```
with:
    upload-plan-destination: 'azure'
    upload-plan-destination-azure-storage-account: 'account_name'
